# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Magic Convert is a WordPress plugin that serves autogenerated **WebP and AVIF** images to browsers that support them. It is a fork of [WebP Express](https://github.com/rosell-dk/webp-express) (by Bjørn Rosell), forked at v0.25.14, with three goals that shape the whole codebase:

1. **Concurrency-safe parallel bulk conversion** of large media libraries (50k+ images) — upstream was strictly serial and not multi-writer-safe.
2. **AVIF output** alongside WebP (a real multi-format abstraction, not find-and-replace).
3. **Native settings-aware nginx config generation** (upstream only handled Apache `.htaccess`).

Naming: PHP namespace `MagicConvert` (was `WebPExpress`), constants `MAGIC_CONVERT_*`, text-domain/slug `magic-convert`, content dir `wp-content/magic-convert/`. **Only brand strings were renamed in the fork** — the literal `webp` / `.webp` / `image/webp` / `webp-images/` and all `rosell-dk/webp-convert` library calls intentionally remain. Do not "fix" them to magic-convert/avif.

The upstream remote (`rosell-dk/webp-express`) is kept configured to pull security fixes. `vendor/rosell-dk/*` is **never modified in place** — generalizations live in `lib/` or in code forked into `lib/classes/AlterHtml/`.

## Commands

```bash
composer install                          # install prod + dev deps (reproducible from composer.lock)
composer test                             # full unit suite (== vendor/bin/phpunit)
vendor/bin/phpunit --filter testName      # run a single test method
vendor/bin/phpunit tests/AvifStackTest.php  # run one test file
composer ci                               # composer validate --strict, then phpunit (local CI gate)
composer build                            # build dist/magic-convert-<version>.zip (== bash bin/build-zip.sh)
# Standalone regressions — run directly with plain php, NOT via phpunit (its bootstrap loads
# vendor/autoload and would mask the very preconditions these guard). CI runs all four.
php tests/regression/avif-autoloader-standalone.php          # AVIF lazy vendor-autoloader
php tests/regression/provider-laziness-standalone.php        # FormatProvider fact methods stay vendor/WP-free
php tests/regression/avif-subprocess-isolation.php           # AVIF encode runs in an isolated child process (SKIPs w/o GD AVIF)
php tests/regression/avif-vips-isoperational-standalone.php  # VipsAvif::isOperational() no-segfault (SKIPs w/o vips)
```

There is no lint script. CI's lint job is a `php -l` sweep over every non-vendor `.php` file plus `composer validate --no-check-all --strict`. CI (`.github/workflows/ci.yml`, on push to `master` + every PR) runs the lint + test jobs on PHP 8.1 and 8.3, regenerating `vendor/composer/` maps fresh from `composer.lock` each run.

Requirements: PHP **8.1+** (needed for GD `imageavif()`, used by the AVIF core), Composer 2.x, WordPress 5.9+.

## Architecture

### Two cross-cutting invariants — internalize these first

**1. The lazy vendor autoloader.** The plugin **never** registers Composer's `vendor/autoload.php` globally — front-end image serving must stay lean. `magic-convert.php` only registers a tiny `spl_autoload_register` for the `MagicConvert\` namespace (mapping `MagicConvert\Avif\AvifStack` → `lib/classes/Avif/AvifStack.php`). **Any code that touches a vendor class (`WebPConvert\…`, `ExecWithFallback`, `LocateBinaries`, the kub-at HTML parser) must pull the autoloader in first.** The chokepoints that do this: `ConvertHelperIndependent::convert()`/`serveConverted()`, `AvifStack::ensureVendorAutoloader()` (in its constructor), and `AlterHtmlInit`. A past bug fataled because the WebP path happened to load the autoloader but the AVIF path did not — `tests/regression/avif-autoloader-standalone.php` guards this and is deliberately run **outside** PHPUnit (the PHPUnit bootstrap loads vendor/autoload and would mask the bug). `FormatProvider` fact methods are vendor-free by contract (pinned by `tests/regression/provider-laziness-standalone.php`); provider `encode()`/`encodeWith()` rely on the `ConvertHelperIndependent` chokepoint having loaded the autoloader — providers deliberately have no autoloader guard of their own.

**2. The WordPress-independent core + standalone serving scripts.** A large slice of the code is designed to run **without a WordPress bootstrap** so the request-time image converter is fast: `ConvertHelperIndependent`, `OutputFormat`, `FileLock`, `ShardFilter`, `ConcurrencyAdvisor`, `WodConfigLoader`, `Destination`, `NginxRules`, `PathHelper`, `SanityCheck`. The `wod/` and `wod2/` entry points (`webp-on-demand.php`, `webp-realizer.php`) include **only** `wod/autoloader.php` — no `wp-load.php`. **Calling any WordPress function inside `WodConfigLoader` / `WebPOnDemand` / `WebPRealizer` / `ConvertHelperIndependent` will FATAL.** This is why these classes re-implement path/config logic WordPress would otherwise provide, and why the unit suite can run without WordPress at all (see Testing).

### Config: two derived JSON files with randomized names

Settings live in **two** on-disk JSON files, not WP options (the serving scripts can't read the DB without WP):

- `config.[hash].json` — the canonical WordPress-side config.
- `wod-options.[hash].json` — a **trimmed projection** of the config, produced **only** by `Config::generateWodOptionsFromConfigObj()`, and the **only** file the standalone serving scripts read. A config key does not appear here unless that method copies it.

`[hash]` is a random hash from `Paths::getConfigHash()` (option `magic-convert-config-hash`), part of the CVE-2025-11379 fix that replaced predictable filenames. The hash is baked into the rewrite rules (`&hash=` query param / `HASH` env var), so **changing the hash requires regenerating the `.htaccess`/nginx rules or serving breaks.** `Config::saveConfigurationAndHTAccess()` is the canonical write path: it writes config.json, mirrors a few hot keys (alter-html flags, avif-enabled) into **autoloaded** WP options via `Option`, projects+writes wod-options.json, and regenerates rewrite rules. `Config::loadConfigAndFix()` / `getConfigForOptionsPage()` are the read paths.

WebP encoding settings (quality/converters/jpeg/png/metadata) stay at the **top level** of config — only AVIF owns a `formats.avif` block. `formats.webp` is just `{enabled:true}`. `Config::enabledFormatIds()` is the single source of truth for which formats a run produces (AVIF is **off by default** → `['webp']` → every consumer takes its existing single-format path, byte-for-byte equivalent to upstream).

### Conversion core (one image → one encoded file)

All callers (admin AJAX, REST, bulk, CLI) funnel through `Convert::convertFile()` → the WordPress-free `ConvertHelperIndependent::convert()`, which is the **single encode chokepoint**: lazy-loads vendor autoload, acquires a `FileLock` on `<dest>.lock`, applies skip-if-fresh, writes to a `<dest>.<pid>.tmp.<ext>` temp file, atomic-`rename()`s it, writes a per-format `.md` log, and dispatches on format id: `avif` → `AvifStack`, a named WebP converter → `WebPConvert` `ConverterFactory`, else → the full `WebPConvert::convert()` stack.

- `OutputFormat` is an immutable value object + lazy registry threading format identity (extension, mime, `cacheDirName` = `webp-images`/`avif-images`) through every path. `coerce(null)` → `webp`, which keeps un-threaded call sites unchanged. Adding a format is essentially a registry entry.
- **Two distinct converter id-spaces:** top-level `config['converters']` is the WebP stack (cwebp/vips/imagick/gd/…); `config['formats']['avif']['converters']` is the AVIF stack (imagick/vips/gd/magick-binary/avifenc/cavif). They share some names but are different code paths. AVIF ids may contain `-`, so `Validate::isConverterId()` does NOT apply — AVIF is whitelisted against `AvifStack::defaultConverterIds()`.
- `lib/classes/Avif/` is the in-tree AVIF encoder stack (WebP is delegated to the vendored library). `AvifStack` tries converters in priority order until one succeeds. `defaultConverterIds()` (plain strings, no heavy class instantiation) must stay in lock-step with `defaultConverters()` and `makeById()`.
- **Security-critical:** `convertFile()` runs `Paths::findImageRootOfPath()` containment check for *every* caller — this is the CVE-2019-15330 (arbitrary file disclosure) guard. `runConversion()` / `resolveImageSourcePath()` exist so the check is shared, never bypassed. Never add a path that reaches `convert()` without it.

### Parallel bulk conversion (the headline feature)

Two drivers feed the one shared, lock-guarded core; design goal is **zero config** (detect resources, adapt — no knobs):

- **Browser path:** `bulk-convert.js` opens the popup → `GET magic-convert/v1/unconverted` runs the filesystem scan **once** (`BulkConvert::getList()`), persists a flat list to `wp-content/magic-convert/bulk-lists/<id>.json`, returns page 1 + `ConcurrencyAdvisor` recommendations. The JS is an **adaptive promise pool** (AIMD: additive-increase after successes, multiplicative-decrease on busy/5xx/429/timeout, with a learned soft ceiling + cooldown to damp oscillation). It expands each item into one work unit per missing format and `POST`s `magic-convert/v1/convert` per unit. REST is `manage_options` + `X-WP-Nonce` (`wp_rest`).
- **CLI path:** `wp magic-convert convert` is parallel-by-default. The parent decides proc count (`ConcurrencyAdvisor::recommendedCliProcs()`) and `proc_open`s N children of itself with `--shard=i/n`; each child rebuilds the **identical** list and keeps only its shard via `ShardFilter` (`crc32(groupQualifiedRelPath) % n`), converting inline and emitting a `#MC-SUMMARY` JSON line the parent aggregates. Fan-out is a graceful fallback — if `proc_open` is unavailable it runs sequentially inline.
- `FileLock` uses atomic `fopen($path,'x')` (`O_CREAT|O_EXCL`), **deliberately not `flock()`** (unreliable across FPM workers / NFS). `release()` is token-scoped and stale locks (>600s) are stolen once. Sharding makes work disjoint; the per-file lock is the second line of defense for accidentally-overlapping runs (CLI + browser at once). Don't remove either.

Sharding correctness depends on parent and all children building the **identical list in identical order**, and on hashing the unwrapped path string (a list item may be a plain string *or* a `{path, formats[]}` array — pass the array directly and it stringifies to `"Array"` and collapses every file into one shard).

### Request-time serving (three strategies)

How a visitor ends up with WebP/AVIF, by server type:

1. **Apache `.htaccess`** — `HTAccessRules` (pure text generator) emits redirect-to-existing / webp-realizer / webp-on-demand rules; `HTAccess` (orchestrator) writes them between `# BEGIN/END Magic Convert` markers. mod_rewrite encodes the source path into a redirect to `wod/webp-on-demand.php` (missing `.webp` → `webp-realizer.php`).
2. **nginx** — no per-dir config exists, so `NginxRules` generates artifacts the admin **downloads** and installs (Accept negotiation via `try_files`). `NginxRules` has **no disk-writing method** (security: artifacts embed the config hash and must not be web-accessible); egress is a capability-gated, nonce-verified download endpoint whitelisted by `NginxPanel::resolveArtifactKey`.
3. **HTML alteration** (inside WordPress) — `AlterHtmlInit::setHooks()` buffers/filters page HTML. `AlterHtmlPicture` wraps `<img>` in `<picture>` with a `<source>` per format and is the **only** strategy that can serve AVIF. `AlterHtmlImageUrls` swaps URLs and is **WebP-only by design** (a baked URL can't per-browser negotiate). Both delegate URL→converted-URL mapping + file-exists/size gating to `AlterHtmlHelper`. The `AlterHtml/` classes are forked from `rosell-dk/dom-util-for-webp` (donor hardcodes a single WebP source) and keep the literal `webpexpress-processed` idempotency marker for upstream compatibility.

`wod/` holds the real serving code; `wod2/` is one-line `include '../wod/…'` shims used as a **fallback location** when `wod/` fails server capability tests ("fewer files → fewer permission interactions"). Editing `wod/` logic automatically affects `wod2/`. **On-demand (wod) serving is currently WebP-only** — `WebPOnDemand` hardcodes `OutputFormat::webp()`; the `convert()` AVIF dispatch exists but on-demand AVIF is gated to a later roadmap step.

`web-service/wpc.php` is a separate sibling endpoint (cloud conversion — lets *other* sites use this one as a remote converter), not part of the local visitor path.

### Config / options / admin

- `Option` is a thin get/update/delete shim that switches between `get_option`/`get_site_option` based on `Multisite::isNetworkActivated()`. **Always go through `Option`/`State`** — calling `get_option` directly reads the wrong scope on multisite. `State` stores a small JSON blob in one non-autoloaded option.
- The settings page (`lib/options/page.php`) `include_once`-chains section `.inc` partials in order. **Partials are not standalone** — they assume `page.php`'s in-scope `$config` and render helpers (`helpIcon`, `magicconvert_checkbox`). Section placement is regression-pinned (`tests/OptionsSectionPlacementTest.php`): convert-on-upload/logging/bulk-convert live under `options/general/` because they govern all formats.
- `lib/options/submit.php` (admin-post target) sanitizes every `$_POST` field into a `$sanitized` array (no `$_POST` reads after that), then merges onto the loaded config. AVIF converter-list sanitization is factored into `lib/options/avif-converters-sanitize.php` (pure, `$_POST`-free, unit-tested). Render-only fields (`working`/`error` converter status) and secrets (api-keys, stripped before render) must never reach the persisted files — secrets are re-injected from the old config on save.

**Two unrelated "migration" concepts — don't conflate them:**
- Numbered DB-stamped migrations: `lib/migrate/migrate{N}.php`, gated by option `magic-convert-migration-version` vs constant `MAGIC_CONVERT_MIGRATION_VERSION` (currently `'17'`) in `AdminInit`. Adding one means bumping that constant **and** having the new `migrateN.php` self-stamp the option (a failed step blocks later steps).
- The in-memory config **schema** version `Config::CONFIG_VERSION` (currently `2`), handled purely by `Config::migrateToV2()`/`fix()`, no DB stamp.

`formats.avif.converters` is an **ordered list, not a mergeable map** — `fix()`/`migrateToV2()` must not `array_replace_recursive` it (index-wise merge re-appends defaults → duplicates); `fix()` captures the user list, merges everything else, then restores it verbatim.

## Testing model

`phpunit.xml.dist` defines one suite over `tests/` with strict mode on (`failOnWarning`, `failOnRisky`, `beStrictAboutOutputDuringTests` — any stray output/warning fails the run). Tests are **WordPress-independent**: no WP, no WP test suite, no DB. Only pure logic that runs standalone belongs here; methods that call WP functions, `realpath()`, or read `$_SERVER` are out of scope.

The WP-stubbing seam: classes like `Option`/`Multisite`/`State` live in `namespace MagicConvert`, so an unqualified `get_option()` resolves to `MagicConvert\get_option` **first if defined**. `tests/NginxPanelWpStubs.php` defines those functions inside `namespace MagicConvert` backed by an in-memory store — intercepting WP at that seam without touching the global namespace. `tests/bootstrap.php` mirrors the production autoloader and requires `vendor/autoload.php` (so `WebPConvert\…` resolves). `tests/NginxHarness.php` can boot a real `nginx -t` / HTTP test but **skips** (doesn't fail) when no nginx binary is found, so nginx tests are inert on CI.

## Releases & the dev-vs-prod autoloader (read before touching vendor/)

This repo **commits production `vendor/` packages** (so the zip works without a build step) and keeps the committed `vendor/composer/` autoload maps in the **no-dev (production) state** (they map no PHPUnit/dev packages) — so a raw source install (a release zip **or** a Composer/Bedrock `dev-master` checkout) boots `vendor/autoload.php` with **no `composer install`**, and it can never eager-require the gitignored dev packages. The trade-off: `composer test` from a clean checkout needs `composer install` (or `composer dump-autoload`) **first**, to regenerate the dev maps that map PHPUnit; those regenerated dev maps must **never** be committed — restore them with `git checkout -- vendor/composer/` before committing. Dev packages themselves are gitignored (`/vendor/phpunit/`, `/vendor/bin/`, `/vendor/sebastian/`, `/vendor/myclabs/`, `/vendor/nikic/`, …).

- A released zip must ship the **no-dev** autoloader (a dev autoloader references gitignored dev packages → fatals on a user's site). `bin/build-zip.sh` regenerates a transient no-dev autoloader at build time, archives `git archive HEAD` + that overlay, then restores whatever autoloader it found (working tree left as found). It fails loudly if the archive still contains `vendor/phpunit/`/`vendor/bin/` or if the archived autoloader won't load.
- **Never commit dev-modified `vendor/composer/` maps.** Refresh committed *production* maps only via `composer install --no-dev && composer dump-autoload -o --no-dev` when bumping a production dep.
- `.gitattributes` `export-ignore` strips dev paths from the zip (`tests/`, `docs/`, `.github/`, `bin/`, etc.). But `test/` (singular) is **runtime sample-image fixtures** consumed by `TestRun`/`SelfTestHelper`/`HTAccess` and ships in the zip — do not confuse it with `tests/` (plural, PHPUnit).

Release flow is `composer build` (git-archive zip). The version lives in two places that must stay in sync on release: the `magic-convert.php` plugin header (source of truth — the build reads `Version:` from it) and `README.txt`'s `Stable tag`. (`lib/classes/ConvertHelperIndependent.php` also has a hardcoded `'Magic Convert <version>'` log-header string with a `TODO` to relocate it — it has drifted from releases and is not a maintained sync target.)

See `docs/development.md` (dev setup, concurrency model, vendor-update procedure), `docs/ROADMAP.md` (phased fork plan) for more.
